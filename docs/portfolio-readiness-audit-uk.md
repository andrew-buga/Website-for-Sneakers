# Аудит готовності проєкту **Website-for-Sneakers** до портфоліо

## Короткий висновок

Поточний проєкт виглядає як якісний **frontend-прототип** магазину взуття, але для сильного портфоліо рівня “повноцінний e-commerce” йому бракує production-функціональності: реального backend, безпечної авторизації, стабільної обробки замовлень та збереження клієнтських даних у централізоване сховище (включно з Excel-експортом).

---

## Що вже є (плюси)

- Каталог, cart, checkout, сторінки акаунту (логін/реєстрація/профіль/замовлення).
- Базовий UX-потік для оформлення замовлення.
- Контексти для авторизації, кошика та wish-list.

---

## Що критично не вистачає для портфоліо

## 1) Backend та база даних

Зараз основні дані зберігаються у `localStorage`, тому:
- дані губляться при очищенні браузера;
- немає централізованої бази для всіх користувачів;
- неможливо нормально адмініструвати замовлення.

**Що додати:**
- backend API (Next.js route handlers + DB або окремий сервер);
- БД: PostgreSQL/MySQL + ORM (Prisma/Drizzle);
- серверні моделі: `users`, `orders`, `order_items`, `products`, `addresses`.

## 2) Безпечна авторизація

Паролі не повинні зберігатися у клієнтському localStorage, навіть у базовому “хеші” через `btoa`.

**Що додати:**
- NextAuth або JWT + httpOnly cookies;
- bcrypt/argon2 для хешування;
- валідація на сервері;
- обовʼязкові policy: password strength, rate limiting на login.

## 3) Реальні платежі

Поточний `/api/payment` є імітацією відповіді без інтеграції з платіжним провайдером.

**Що додати:**
- Stripe (Checkout або Payment Intents),
- webhooks (`payment_intent.succeeded`) для фінального підтвердження замовлення,
- збереження транзакційного статусу в БД.

## 4) Збереження клієнтів у Excel

Запит про “збереження даних клієнтів в Excel” краще реалізувати як **експорт** із БД у `.xlsx`, а не як primary storage.

**Що додати:**
- таблицю `customers`/`users` у БД;
- endpoint `/api/admin/export/customers`;
- генерацію Excel через `exceljs` або `xlsx`;
- кнопку в адмінці “Export customers to Excel”.

> Рекомендація: зберігати дані в БД, а Excel робити регулярним експортом (on-demand або за cron).

## 5) Product data / inventory

Наразі товари виглядають як статичні дані (без керування залишками, SKU, актуальними цінами).

**Що додати:**
- товарну модель у БД;
- SKU, sizes, colors, stock;
- блокування checkout, якщо товар out-of-stock;
- просту адмін-панель CRUD товарів.

## 6) Статуси замовлення та кабінет клієнта

Статуси замовлення на фронті є, але без серверного lifecycle.

**Що додати:**
- серверний workflow: `pending -> paid -> shipped -> delivered`;
- API для історії замовлень з пагінацією;
- детальну сторінку замовлення (номер, позиції, адреса, статус оплати).

## 7) Якість для портфоліо (інженерна частина)

Щоб проєкт виглядав як “готовий продукт”, потрібні:
- валідація через Zod на всіх важливих формах;
- обробка помилок API (4xx/5xx) + user-friendly повідомлення;
- тести (мінімум: auth flow, checkout flow, API smoke tests);
- README з архітектурою, ER-діаграмою, інструкцією деплою;
- CI (наприклад GitHub Actions: typecheck + lint + tests).

---

## Мінімальний roadmap (щоб швидко підняти рівень портфоліо)

1. Підключити БД + Prisma, винести `users/orders/products` із localStorage.
2. Впровадити безпечну auth (bcrypt + cookie session/JWT).
3. Замінити mock-payment на Stripe sandbox.
4. Додати Excel-експорт клієнтів (`/api/admin/export/customers`).
5. Додати базові автотести + оновити README.

---

## Результат після доробок

Після цих кроків проєкт можна позиціонувати не як “макет магазину”, а як **повноцінний demo e-commerce застосунок** для портфоліо з реєстрацією, замовленнями, оплатою і вивантаженням клієнтських даних у Excel.
